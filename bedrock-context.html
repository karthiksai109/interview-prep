Dossier 1 · The question that cost you at AT&T

"If you don't pass context to Bedrock, how will it answer?"

The interviewer is probing one idea: do you actually understand that the model has no memory and no knowledge of your data? Once you frame it that way, the deep answer writes itself.

On this page: The mental model · What happens with no context · Context assembly pipeline · Failure modes & detection · Interview answers · Trap follow-ups

The mental model: Bedrock is a stateless inference API

AWS Bedrock is not a chatbot. It's a managed service that fronts foundation models (Claude, Titan, Llama, Mistral) behind two APIs: InvokeModel and Converse. You send a model ID, a messages array, an optional system prompt, and inference config (temperature, maxTokens, topP). It returns generated tokens plus usage metadata.

  • Stateless. Every call is independent. Bedrock remembers nothing between requests. "Conversation memory" is your job — you store history (we used DynamoDB at Verizon) and resend it every turn.
  • Parametric knowledge only. The model knows only what was in its training data, frozen at a cutoff date. It has never seen a Verizon plan catalog, a Citi policy manual, or any user's account.
  • Zero tools by default. It can't look anything up unless you retrieve and inject that material into the prompt — or you use Bedrock Agents / Knowledge Bases, which are AWS's managed wrappers doing that orchestration for you.

So what happens with no context?

It still answers — fluently. That's the trap. Without context the model draws on parametric knowledge, giving you:

  1. Generic answers. "How do I dispute a charge?" returns the textbook Reg E answer — not your bank's process, form, or SLA.
  2. Hallucination on private facts. Ask about an internal product and it will invent plausible detail, because LLMs produce likely text rather than admitting "I don't know."
  3. Stale answers. Anything after the training cutoff — new rates, renamed plans — is invisible to it.
  4. No personalization. With no profile or session injected, every user is treated identically.
60-second interview answer
"Bedrock is a stateless inference API — the model has no memory and no knowledge of our data. With no context it answers purely from its training distribution: generic at best, hallucinated at worst on anything company-specific. That's why our pipeline treated context assembly as a first-class stage: the router classified intent first, we retrieved the scoped policy chunks the selected agent owned, injected profile facts from the session store, assembled everything under a token budget, and sent it through the Converse API. And we built a guard: if retrieval returned nothing above our similarity threshold, the agent said 'I don't have enough information' instead of guessing."

Token budget with priority truncation. The context window is a cost-and-latency budget, not just a hard limit. When the assembled prompt overflows, you evict by priority: system rules and retrieved facts stay; oldest conversation turns are summarized or dropped first. This is the detail that makes senior interviewers nod.

Failure modes and detection

Too little context

Generic or hallucinated answers. Detect with faithfulness evals (does the answer cite retrieved text?), retrieval hit-rate metrics, and thumbs-down feedback events streamed to Datadog.

Too much context

Cost and latency scale with input tokens; attention degrades over long prompts ("lost in the middle"). Fix with reranking to fewer, better chunks and capped, summarized history.

Wrong context

Confidently wrong answers with citations — the most dangerous failure. Fix with per-agent scoped indexes, metadata filters, and an eval-on-failure loop where flagged answers become regression tests.

Guardrails as the safety net

Bedrock Guardrails add denied-topic filters and PII redaction independent of the model — belt-and-suspenders for when the context layer misbehaves. In a bank, this layer is mandatory.

The full 2-minute answer

Open the recitable deep answer

"Bedrock doesn't know anything by itself. It's a stateless API over foundation models — the only knowledge in any call is what I put in the request. So with no context, the model falls back on its parametric training knowledge: fine for generic questions, dangerous for anything about our plans, policies, or the specific user, because it answers fluently whether or not it's right.

In the Verizon platform we treated context as a pipeline. The router classified intent first, which told us which agent — and therefore which scoped knowledge index — the query needed. We retrieved top-k chunks with a similarity threshold, pulled the user's profile facts and recent turns from the DynamoDB session store, assembled everything under a token budget with priority truncation, and called Bedrock Runtime with the agent's system prompt. Latency and input/output token counts for every call went to Datadog, so context-size creep was a monitored metric, not a surprise.

The failure case you're describing — insufficient context — was an explicit code path: retrieval below threshold produced an honest 'I don't have that information, let me route you' response instead of a guess, and those events were logged to become new eval cases. Guardrails sat in front of the model as an independent PII and denied-topic layer.

So the short answer: with no context it answers from its training distribution — which is precisely the failure mode the whole context pipeline exists to prevent."

Trap follow-ups they chain on

"Why not fine-tune the model on your data instead of injecting context?"

Fine-tuning changes behavior and style, not factual knowledge — and it freezes knowledge at training time, same as the base model. Your policy docs change weekly; retraining for every doc edit makes no sense. RAG keeps facts in an index you can update in minutes, gives you citations, and lets you scope permissions per document. Fine-tuning has a real role (output format, domain tone, classification heads) but it's not a knowledge-injection mechanism. Also: cost, eval complexity, and governance review per model version in a regulated environment.

"How do you know the model used the context you gave it?"

Faithfulness evals — automated checks that answers cite or paraphrase retrieved chunks rather than outside claims. We also ran a golden Q&A set with known correct sources in CI, tracked retrieval hit-rates, and sampled production answers for human review. If faithfulness drops after a prompt or index change, the pipeline flags it before users do.

"What if the retrieved context itself is wrong or outdated?"

Then you get confidently wrong answers with citations — the worst failure. Defenses: freshness metadata on every chunk with effective dates, a scheduled re-indexing job, document ownership so stale sections have an accountable team, and an answer-flagging feedback loop that traces bad answers back to the specific source chunk. At a bank this becomes a document-governance problem, not just a search problem.

"Would you use Bedrock Knowledge Bases instead of your own retrieval?"

Knowledge Bases is the managed version of exactly the pipeline I described — S3 data source, chunking config, Titan embeddings, OpenSearch Serverless as the vector store. For a fast-moving internal tool I'd take it. We built custom because we needed scoped per-agent indexes, our own hybrid BM25-plus-vector retrieval, and custom metadata filtering, which exceeded what the managed abstraction exposed at the time. The honest answer is: managed first, custom when you hit its ceiling.

Do not say
"Bedrock would use its memory from previous questions" — it has none — or "we trained the model on our data" when you mean RAG. Conflating fine-tuning with retrieval is the fastest way to lose a final round on this topic.
