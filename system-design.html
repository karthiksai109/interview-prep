System Design: Backend + LLM Systems

Citi will likely give you a design prompt tied to your experience: either "design the agent platform you built" or "design X for a bank." Every walkthrough below follows the same discipline: requirements → numbers → components → tradeoffs → what breaks.

On this page: The 5-step method · Design: agentic chat platform · Design: real-time analytics ingestion · Design: compliant document Q&A for a bank · Backend tropes you must know cold

The 5-step method (use it aloud)

1. Clarify requirements→ 2. Back-of-envelope numbers→ 3. Draw components→ 4. Deep-dive 2–3 areas→ 5. Failure modes & tradeoffs

Step 2 is where juniors die. Always bring numbers: QPS, payload size, p95 latency target, token budget, storage growth. Interviewers grade estimation instinct more than box-drawing.

Design prompt: "Walk me through the agentic platform you built"

Full whiteboard narrative (~3 minutes)

Requirements: multi-agent assistant for telecom customers, sub-2s perceived responses, per-domain expertise, exec KPIs, auditable. Non-goals: training models.

Numbers: if internal rollout, assume tens of thousands of sessions/day; average conversation ~6 turns; average call ~2k input tokens / 400 output tokens → plan the Bedrock quota and per-request cost accordingly; p95 per-call latency target ~1s so streaming makes UI feel instant.

Components: Next.js/React chat shell on CDN edge → API Gateway → Lambda handlers (serverless: spiky traffic, scale-to-zero, event-driven) → router agent → 6 specialist agents (own prompt/tools/scoped index) → Bedrock Runtime for inference; DynamoDB for sessions/profiles; vector store per agent; Datadog RUM + Bedrock token metadata; QuickSight for exec KPIs. CI/CD from GitHub with protected branches; Docker for the non-serverless services.

Deep-dive picks: (1) context assembly + token budgeting, (2) routing policy with confidence thresholds and session stickiness, (3) observability: every call emits latency, tokens, agent id — so cost and quality are attributable per agent.

What breaks: router misclassification under vague queries (clarifying-question path); Bedrock quota throttling at burst (queue + graceful degradation to a smaller model); context creep (summarize history); stale index (versioned re-indexing); prompt injection via retrieved text (untrusted-data treatment, tool authz).

Design prompt: "Design a real-time analytics ingestion service" (your Epsilon work)

Full whiteboard narrative

Requirements: 50,000+ events per batch, sub-200ms API response, live dashboards, anomaly detection over 100k events in under 3s.

Flow: FastAPI ingest endpoints (async I/O, Pydantic validation) accept batches → immediately return 202 after durable enqueue → Kafka topics partitioned by tenant/event-type → consumer workers enrich + write to PostgreSQL (transactional aggregates), MongoDB (flexible payloads), Elasticsearch (search/lucene queries) → WebSocket/SSE fan-out to React dashboards. JWT + rate limiting at the edge; Celery/RabbitMQ for heavier background report generation.

Why Kafka here, RabbitMQ/Celery there: Kafka is a durable, replayable, partition-ordered log — right for high-throughput event streams and re-consumption by new consumers. RabbitMQ/Celery is a task broker — right for job dispatch with routing and acks. Saying this clearly is a senior signal.

Reliability: idempotency keys on ingest, consumer retry with exponential backoff, dead-letter queues, backpressure by partition lag monitoring in Grafana/Datadog.

Failure modes: poison messages → DLQ; hot partition → key strategy review; consumer lag spike → scale consumers (K8s HPA on lag); ES cluster saturation → bulk-request tuning and queue buffering.

Where AI plugs in: scoring is a separate inference service called from consumers (API-based model endpoints), or batch inference reading from the stream — keeps model rollout independent from ingest. Anomaly scoring is assistive; anything alert-worthy goes through deterministic thresholds first (same dual-layer safety principle as HealthGuard: rules first, ML as context).

Design prompt: "Design compliant document Q&A for bank employees"

Full whiteboard narrative

Requirements: employees ask policy questions; answers must cite documents, respect document-level permissions, and be auditable end-to-end. No customer PII on output.

Architecture: SSO front → API gateway (JWT, rate limit) → query service → permission filter (user's entitlements join against document ACL metadata — before retrieval, never after) → hybrid retrieval over ACL-scoped index partitions → rerank → prompt assembly with citation requirement → LLM via model gateway (Bedrock) → answer with chunk citations → everything (query, retrieved chunk ids, prompt version, model, tokens, answer) written to an append-only audit log.

The banking-specific moves: ACL filtering pre-retrieval (security, not politeness); PII redaction on ingest and again via guardrails on output; prompt + model + index all versioned so any historical answer can be reproduced; abstention below similarity threshold with escalation to the policy team; eval golden set as a deploy gate (model risk management discipline).

Tradeoffs to name: managed Knowledge Bases vs custom (governance needs argue custom ACL handling); per-partition indexes vs metadata filters; streaming UX vs complete-answer redaction (redact server-side before streaming, or buffer).

Backend tropes you must be able to defend

Microservices: services/api, services/rag, ui — call that out as an example

Independent deploys and failure isolation vs operational overhead (tracing, versioning contracts). Your bank-complaint-copilot is a clean small example to cite: three services, REST contracts, compose file.

JWT rotation & rate limiting

Short-lived access tokens + rotating refresh tokens limit stolen-token blast radius; store refresh tokens hashed; reuse detection revokes the family. Rate limiting via token bucket in Redis per principal; return 429s with Retry-After. Pair with immutable audit logs for an end-to-end security story that matches your CV's security bullet exactly.

Kubernetes deployment discipline

Health probes (liveness vs readiness), HPA on CPU or on Kafka lag/custom metric, rolling deploys with surge limits, resource requests/limits, Terraform-managed infra so clusters reproduce — the exact words on your Environment line, in a coherent sentence.

TDD/quality pipeline

Pytest unit + integration suites run in GitHub Actions/Jenkins; SonarQube static quality gates and Veracode SAST for security findings; protected branches; staged deploys. If asked "how do you keep AI code tested": golden-set evals in CI + contract tests on tool schemas + prompt snapshot tests.

The sentence to open any design answer with
"Let me confirm requirements and throw out rough numbers first — QPS, latency budget, and data volume change every downstream decision." It reframes you from candidate to colleague in the first 20 seconds.
