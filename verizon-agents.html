Architecture walkthrough (the whiteboard version)

React 18 / Next.js 14 chat UI (CDN edge cache)→ API Gateway + Lambda front door→ Router / orchestrator agent→ 6 specialist agents→ Bedrock Runtime (inference)
DynamoDB: sessions & profiles Vector index: scoped agent knowledge Datadog: RUM + latency + tokens QuickSight: exec KPIs
  1. Front end. Modular chat UI across 8 modules (React 18, Next.js 14, TypeScript), message persistence, deployed static/edge via GitHub CI/CD — that's how you hit AI response cold-start under 2s: no server round-trips for the shell, CDN-cached assets, only the inference path hits AWS.
  2. API layer. Serverless API routes → AWS Lambda. Chosen for spiky chat traffic (scale-to-zero when idle; auto-scale at burst) and event-driven integration with the rest of the cloud estate.
  3. Router agent. Classifies intent and dispatches to the right specialist. Covered deeply in the routing section.
  4. Six specialist agents. Each is an isolated unit: own system prompt, own scoped knowledge index, own tool set, own model selection, own eval suite. Example split: billing & payments, network/troubleshooting, plans & upgrades, device support, onboarding/discovery, and a generalist fallback.
  5. Bedrock Runtime SDK. Each agent calls the Converse API through the runtime; we captured latency, input/output token counts, and agent metadata on every call for performance tracking in Datadog.
  6. State. DynamoDB holds session records: conversation turns, user profile facts, agent-in-charge for the session. Stateless Lambdas read/write the store per turn.
  7. Observability & reporting. Datadog RUM on the client for real user latency and errors; QuickSight dashboards for exec KPIs (usage trends, agent mix, deflection rate).

"How are agents assigned — on what basis?"

Answer this in three layers. Most candidates stop at layer 1.

Layer 1 — the routing signal

  • Intent classification. The router reads the query (plus last few turns) and picks the target agent. Three ways to implement, cheapest first: keyword/rules for obvious cases → a small ML intent classifier for the fat middle → an LLM router call for ambiguous cases. An LLM router adds a round-trip of latency, so you don't pay it on every message.
  • Capability manifests. Each agent declares what it handles (skills, tools, knowledge scope). The router semantically matches the task against those descriptions — this is exactly the model Google's A2A protocol formalizes with Agent Cards: name, skills, endpoint, so orchestrators can discover and route without hardcoding.
  • Session continuity. Within an active session we weighted the current agent — don't re-route mid-task just because a follow-up phrasing looks cross-domain.

Layer 2 — the confidence policy

Routing confidence below threshold → ask a clarifying question or fall to the generalist agent, never guess into a specialist. Misrouting is worse than a clarifying question: it burns a specialist's narrower context window on the wrong problem and erodes trust.

Layer 3 — operational bases

  • Cost/latency: cheap small model for chit-chat-tier intents, larger model reserved for complex reasoning.
  • Permissions: some agents hold tool access others never get (e.g., account-lookup tools gated behind authz checks).
  • Load: in a scaled deployment you can also shard by agent concurrency and throttling — Bedrock has per-model quotas, so routing is also quota-aware.
60-second interview answer
"Agents were assigned by intent, with continuity and confidence policies on top. The router classified the query against each agent's declared capability manifest — the same idea A2A later formalized as Agent Cards — with sticky sessions so follow-ups stayed with the agent mid-task. High-confidence matches dispatched directly; below threshold we asked a clarifying question or fell back to the generalist, because a wrong specialist costs more than one extra turn. Model choice per agent was cost- and latency-based: smaller models for simple intents, frontier model only where reasoning justified it."

"How did you ingest data for the LLM?"

Sources: help docs, PDFs, ticket history, FAQs→ Parse & normalize→ Chunk (recursive, overlap, heading-aware)→ Metadata + PII scan→ Embed (Bedrock Titan Embeddings)→ Index (vector store, HNSW)

Then at query time: hybrid retrieval (BM25 keyword + vector similarity) → rerank → top-k chunks injected into the agent's context. Details that earn depth credit:

  • Chunking tradeoffs. Fixed-size with ~10–15% overlap is the baseline; heading/structure-aware splitting keeps a policy section's context together. Oversized chunks dilute cosine similarity; undersized ones lose antecedents. 500–800 token chunks are a practical middle.
  • Metadata is the unsung hero. Every chunk carried source, section, product, and effective-date. Metadata filters let agents query only their scope, and freshness fields enabled stale-content detection.
  • Per-agent scoped indexes. Rather than one giant index, each agent retrieved from its partition — higher precision, fewer cross-domain leaks, cleaner governance.
  • Refresh & versioning. Scheduled re-indexing with dedupe; index versions tagged so a bad ingestion could be rolled back like code.
  • PII hygiene before embedding. Anything personal is stripped or masked before it becomes an embedding — embeddings are not a privacy boundary.
60-second interview answer
"Ingestion was ETL into a vector index: parse and normalize sources, chunk with overlap and structure awareness, attach metadata — source, section, effective date, owning agent — scan for PII, embed with Titan Embeddings through Bedrock, and index into per-agent scoped partitions. At query time the agent ran hybrid BM25-plus-vector retrieval, reranked, and injected top-k into its prompt under the token budget. Re-indexing was scheduled and versioned so we could roll back a bad corpus the way you'd roll back a deploy."

"Why six agents instead of one big agent?"

  1. Prompt isolation. A single system prompt holding six domains is a prompt-injection and instruction-conflict magnet; six scoped prompts are individually maintainable and testable.
  2. Blast radius. A regression in the billing agent's prompt doesn't degrade network troubleshooting. Per-agent deploy + rollback through normal CI/CD.
  3. Scoped tools & permissions. Principle of least privilege: only the agent needing account lookup holds that tool.
  4. Scoped retrieval. Per-agent indexes beat filters on a monolith: precision, governance, and per-domain refresh cadence.
  5. Independent economics. Per-agent model choice and eval thresholds let you optimize cost and quality where it matters.
Do not say
"Microservices are just better." The interviewer wants the agent-specific reasons: prompt isolation, tool scoping, scoped knowledge, per-agent evals — not generic SOA talking points.
